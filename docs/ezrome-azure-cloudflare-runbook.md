# EZROME Azure–Cloudflare Owner Runbook

This runbook turns the EZROME architecture blueprint into a controlled deployment sequence. It is intentionally written with placeholders. Replace each placeholder only inside the Azure portal, Cloudflare dashboard, or GitHub secret settings; never commit the values to the repository.

## 1. Prepare ownership

Confirm that you are signed into the Azure subscription that will own EZROME and the Cloudflare account that contains the `ezrome.co.za` zone. The connected Cloudflare account currently does not expose that zone, so DNS work must stop until the correct account is connected or the domain is added to the intended account.

Create a staging environment before production. Use a separate resource group such as `ezrome-staging-rg` and a separate database or schema. Production data must not be used for deployment testing without an approved backup and rollback plan.

## 2. Create Azure resources

Create these resources in the selected Azure region:

| Resource                  | Suggested name            | Purpose                         |
| ------------------------- | ------------------------- | ------------------------------- |
| Resource group            | `ezrome-staging-rg`       | Lifecycle boundary for staging  |
| Static Web App            | `ezrome-staging-web`      | React/Vite frontend             |
| Container Registry        | `ezromestagingacr`        | Stores the API image            |
| Container App environment | `ezrome-staging-env`      | Runtime environment for the API |
| Container App             | `ezrome-staging-api`      | Express/tRPC backend            |
| MySQL server/database     | owner-selected name       | Drizzle/MySQL data store        |
| Storage account/container | owner-selected name       | Videos and thumbnails           |
| Application Insights      | `ezrome-staging-insights` | API and deployment monitoring   |

Use private networking and restricted firewall rules where the selected Azure plan supports them. Enable TLS for the database and storage access. Keep resource names stable after deployment because the GitHub workflow uses the resource identifiers as settings.

## 3. Configure the frontend deployment

The repository contains `.github/workflows/azure-static-web-apps.yml`. In the GitHub repository settings, create an Actions secret named `AZURE_STATIC_WEB_APPS_API_TOKEN` using the deployment token generated by the Azure Static Web App. The workflow builds the frontend with `pnpm build:frontend` and uploads `dist/public`.

The workflow is token-gated. If the secret is absent, it reports that deployment was skipped instead of failing or attempting an unauthorized upload.

## 4. Configure the API deployment

The repository contains `deploy/azure/api/Dockerfile` and `.github/workflows/azure-api-container-app.yml`. Add the following GitHub Actions secrets:

| Secret                     | Value source                                              |
| -------------------------- | --------------------------------------------------------- |
| `AZURE_CLIENT_ID`          | Federated workload identity or approved service principal |
| `AZURE_TENANT_ID`          | Azure tenant identifier                                   |
| `AZURE_SUBSCRIPTION_ID`    | Azure subscription identifier                             |
| `AZURE_RESOURCE_GROUP`     | Resource group containing the Container App               |
| `AZURE_CONTAINER_APP_NAME` | Container App resource name                               |
| `AZURE_CONTAINER_REGISTRY` | Registry name without `.azurecr.io`                       |

Configure the Container App runtime environment with the actual application settings, including `DATABASE_URL`, `JWT_SECRET`, OAuth settings, storage configuration, and any retained managed-AI integration values. These runtime values belong in Azure application settings, not GitHub source files.

The API workflow builds an image from the repository root, pushes it to Azure Container Registry, and updates the Container App to the commit-tagged image. It is also token-gated and skips deployment until the required Azure settings exist.

## 5. Configure Cloudflare after staging succeeds

Only after the Azure staging frontend and API pass smoke tests should you configure the public domain. In Cloudflare:

1. Confirm that `ezrome.co.za` is present in the correct account.
2. Add the Azure frontend hostname as the origin for the selected web record.
3. Add `www` as a redirect or canonical alias according to the chosen public URL.
4. Add `api.ezrome.co.za` only if a separate API hostname is required.
5. Enable proxying and edge security gradually after DNS-only origin validation.
6. Add rate limits for login, upload, reporting, and other abuse-sensitive endpoints.
7. Configure Email Routing for `support@ezrome.co.za` and `copyright@ezrome.co.za` only after verifying the destination inbox.

Do not guess Azure hostnames, IP addresses, MX records, or verification tokens. Copy them from the active Azure and Cloudflare dashboards.

## 6. Staging smoke tests

Before production cutover, test the following against the Azure staging hostname:

| Area            | Verification                                                                           |
| --------------- | -------------------------------------------------------------------------------------- |
| Frontend        | Direct navigation to nested React routes returns the application shell                 |
| Authentication  | Sign-in, session persistence, logout, and protected routes work                        |
| Creator Studio  | Upload, thumbnail handling, storage key encoding, and creator download permission work |
| Offline library | Download state, rights checks, and limited offline playback behave correctly           |
| Governance      | Reporting, moderation, account deletion request, and cancellation/appeal states work   |
| Newsroom        | Source states, approval workflow, and human-in-the-loop controls work                  |
| Database        | Drizzle migrations and read/write operations target the staging database only          |
| Monitoring      | API errors and latency appear in Application Insights                                  |
| Security        | Secrets are absent from built client assets, logs, and Git history                     |

## 7. Production cutover and rollback

Before changing Cloudflare production records, export or back up the current database and confirm the rollback owner. Lower DNS TTL only according to the approved change plan. Switch the web origin to Azure, verify the custom domain and TLS certificate, then test the public smoke-test list again.

Keep the current Manus deployment available as the rollback reference. If authentication, media, database, or reporting behavior fails, revert the Cloudflare origin to the previous deployment and investigate Azure separately. Do not delete the previous deployment until the agreed observation period has passed.

## 8. Owner-controlled launch items

This repository provides the code and deployment scaffolding, but the owner must still complete Azure subscription ownership, Cloudflare zone access, secret entry, database provisioning, DNS cutover, legal publication, Play Console setup, Android signing, billing configuration, and closed testing with real devices.
